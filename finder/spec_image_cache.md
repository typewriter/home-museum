# 画像キャッシュの設計

館のサーバーへの負荷を抑えつつ画像を表示するための仕組み。取得を館ごとに
10 秒に 1 回へ絞り、リサイズして WebP にしたものを Cloudflare R2 に無期限で置く。

実装は `internal/imagecache/`、状態は `finder/cache.db`。

## 1. キーは `images.id` ではなく `sha256(source_url)`

`spec_schema.md` §1 は「派生層は数分で作り直せる」という理由で `images.id` を
派生テーブルのキーにしている。**画像キャッシュにはこれが当てはまらない。** 館ごと
10 秒では Rijksmuseum だけで 80 日かかり、作り直せない。`images.id` をキーにすると
hm.db の再構築で全キャッシュが迷子になる。

URL 上は `images.id` を使い (`/img/{id}/{width}`)、サーバーが `source_url` の
ハッシュに変換する。URL と保管の名前空間を分けておけば、id が変わっても保管側は
無傷で済む。

## 2. 失敗も無期限に記録する (ネガティブキャッシュ)

「有効期限は無期限」は成功だけでなく**失敗にも要る**。記録しないと、404 の画像が
毎回キューに戻り館を延々と叩き続ける。404 / 410 / 画像でないものは `gone` にして
二度と取りに行かない。

### Cloudflare のチャレンジは `gone` にしなかった

AIC の `cf-mitigated: challenge` は、IIIF サーバーへの過負荷時にだけ動的に有効化
される DDoS 対策で、UA + Referer を揃えれば平常時は通る
(github art-institute-of-chicago/data-aggregator#151)。`gone` にすると負荷が
引いた後も復帰できないので、一時失敗として再試行する (§3 の AIC 専用間隔と対)。

## 3. レート制限は館ごと

負荷は館ごとに独立しているので、館単位で 10 秒空ければ目的を達する。6 館並列で
実効 6 倍になり、キューが伸びにくい。

`server/app.rb` の同期設計 (同じ分の全クライアントが同じ作品を見る) を維持するなら、
新規に必要な画像は視聴者数によらず毎分 1 枚なので、10 秒に 1 回でも 6 倍の余裕がある。

### AIC だけ 30 秒に 1 回

§2 の動的チャレンジは 10 秒間隔でも再びトリガーしうるので、再発の確率を下げる。

### 429 は Retry-After を尊重する

10 秒間隔の自主規制は、相手が制限を明示してこない館向けのもの。Wikimedia は 429 と
`Retry-After` で待ち時間を明示してくる (WDQS で 13〜600 秒を実測)。

指定と指数バックオフの**大きい方**を採る。指定より長く待つのは礼儀に反しないが、
短い指定に従って叩き過ぎるのは避けたい。上限は指数バックオフと同じ 24 時間にそろえる。
異常に大きい値を返す相手に、無期限に固着しないため。

## 4. IIIF には 1600px を要求する (55%)

`aic` と `rijksmuseum` の 752,463 件 (全体の 55%) は IIIF で、現在の `image_url` は
`full/full` / `full/max` = 原寸を指している。IIIF のサイズ指定に書き換える。

Rijksmuseum の 1 枚での実測:

| 館に要求 | 館の転送量 | 生成される WebP |
|---|---:|---:|
| `full/1600,/` | **1.25 MB** | 0.876 MB |
| `full/2400,/` | 2.80 MB | 0.932 MB |
| `full/max/` | 2.96 MB | 0.928 MB |

館の転送量が 58% 減り、出力もむしろ小さい。二重圧縮による劣化は PSNR で
比べようとしたが、館側リサイズと自前リサイズでは 1px 単位の幾何がずれ、PSNR が
サブピクセルのずれに極端に敏感なため意味のある数字にならなかった (22.8 / 24.9 /
35.5 dB と出たが、これは圧縮ではなく位置ずれを測っている)。**この点は未検証**。

残る 4 館 (609,534 件) は原寸を取って自前で縮小する。

Wikimedia は IIIF ではないが、`Special:FilePath` に `?width=` を付けると縮小版へ
リダイレクトするので、同じ発想で 1600px を要求する。

## 5. 変換は libvips に外出しする

**Go には実用的な lossy WebP エンコーダが純 Go で存在しない。** `nativewebp` は
ロスレス (VP8L) 専用で写真では JPEG より大きくなる。使えるのは cgo の
`chai2010/webp` か `kolesa-team/go-webp` だけで、どちらも finder の
「cgo なしで `go build` だけ通る」性質を壊す。

CLI (`vipsthumbnail`) に外出しすればこの問題は消える。`cwebp` ではなく libvips を選ぶ理由は **shrink-on-load**。`cwebp` はリサイズ前に
JPEG をフルデコードするため、Paris Musées の 4415×5004 では 66 MB のビットマップを
展開することになる。libvips は DCT 段階で 1/2・1/4・1/8 に縮めながら読む。

実測 (原寸 → 1600px + 400px、ICC の sRGB 変換込み):

| source | 元 | 1600px | 400px | 時間 | 最大メモリ |
|---|---:|---:|---:|---:|---:|
| rijksmuseum (IIIF 1600) | 1.25 MB | 0.898 MB | 0.065 MB | 1.48s | 126 MB |
| aic (IIIF 1600) | 2.00 MB | 0.854 MB | 0.036 MB | 1.42s | 137 MB |
| cleveland | 1.16 MB | 0.102 MB | 0.008 MB | 0.57s | 115 MB |
| met | 0.54 MB | 0.038 MB | 0.004 MB | 0.42s | 116 MB |
| parismusees | 6.44 MB | 0.692 MB | 0.025 MB | 1.17s | 128 MB |
| smithsonian | 8.70 MB | 0.280 MB | 0.015 MB | 0.67s | 128 MB |

10 秒に 1 回なら CPU デューティ比 5〜15% (1 コア)。`VIPS_CONCURRENCY=1` で
1 コアに抑える。

### 符号化オプションの根拠

Q=80 で 6 枚の合計:

| 設定 | 合計 | 時間 |
|---|---:|---:|
| 既定 (`effort=4`, ss=off) | 2.903 MB | 2.56s |
| `effort=6` | **2.805 MB** | 5.08s |
| `effort=6` + `smart_subsample` | 2.865 MB | 5.20s |
| + `preset=photo` | 2.965 MB | 5.25s |

- `effort=6` — 3.4% 縮む。時間は倍だが 10 秒に 1 回なので無関係
- `smart_subsample` — サイズ +2.1%、PSNR ほぼ不変。**PSNR は輝度支配なので
  クロマのにじみを測れない。**WebP の lossy は常に 4:2:0 で、彩度の高い細部が
  滲む。美術作品ではこの 2% を払う
- `preset=photo` — サイズも PSNR も悪化。使わない
- `strip` は libvips 8.15 で非推奨。`keep=none`

### なぜ JPEG ではなく WebP か

同じ PSNR 36 dB に揃えた比較 (JPEG 側は libjpeg-turbo + `optimize_coding`):

| file | JPEG | WebP | 削減 |
|---|---:|---:|---:|
| rijksmuseum | 1.12 MB | 0.87 MB | 22.6% |
| aic | 1.45 MB | 0.98 MB | 32.4% |
| parismusees | 1.23 MB | 0.82 MB | 33.0% |
| smithsonian | 0.69 MB | 0.52 MB | 24.8% |
| **計** | **4.48 MB** | **3.18 MB** | **28.9%** |

当時の全 1,361,997 件を 1600px + 400px で持つと **約 0.65 TB** (JPEG なら約 0.9 TB)。

## 6. Go で WebP を再デコードしてはいけない

`golang.org/x/image/webp` は lossy WebP を `image.YCbCr` として返すが、**VP8 は
限定レンジ (16–235) の YUV** なのに `image.YCbCr.At()` は JPEG のフルレンジ変換を
当てる。実測で **10 dB (31.80 → 42.16) ずれた**。

したがって 400px サムネを 1600px の WebP から作ってはいけない。**両サイズとも
原本から libvips で生成する**。

同じ理由で、キャッシュ済み画像を Go 側で読み直して加工する処理は入れない。

## 7. ICC は変換してから剥がす

館の画像には AdobeRGB や ProPhoto の ICC プロファイルが埋まっていることがある。
`--export-profile srgb` を通さずに `keep=none` すると色が濁る。sRGB に変換して
から剥がせば、ブラウザの既定解釈 (sRGB) と一致する。

## 8. ミス時はブラウザを待たせない

「取得完了まで待たせる」という要件だが、HTTP コネクションを実際に保持するのは
避ける。キューが深いと数分間ソケットを掴むことになる。

`GET /img/{id}/{w}` は**常に即座に返す**。未取得なら 202 とプレースホルダの SVG を
返し、ページ側の素の JS が `/img/{id}/{w}/status` を数秒おきに見て、`ready` に
なったら `src` を差し替える。待ち位置 (同じ館のキューで自分より前に何枚あるか) を
返すので「あと N 枚 / 約 M 分」と出せる。

**一覧ページに大きい画像を出すと破綻する。** 1 ページ 50 件を一度に要求すると
館ごと 10 秒では数分かかる。詳細ページは 1600px、一覧はサムネ (400px) を
明示的に有効にしたときだけ、という切り分けにする。

## 9. 保管先は差し替えられるようにする

R2 が本番だが、認証情報なしでも動作確認できるよう、ローカルディレクトリに置く
実装も持つ (`-images local:./imagecache`)。

R2 はローカル専用の finder からはプロキシで読む (egress 無料、Class B のみ)。
公開アプリを作る段で public バケット + カスタムドメインに切り替え、帯域を
アプリから外す。

## 10. 出力の検証を挟む

変換が 0 バイトのファイルを残すことがある。`vipsheader` で寸法を確認し、
サイズが 0 でないことを見てから保管先に PUT する。検証に落ちたら `failed`。
