# コレクションの設計

「浮世絵」「印象派」のような主題別の作品集。音楽のプレイリストに当たる。
データとしては 1 コレクションが複数の作品を持つだけで、テーブルは
`collections` と `collection_works` の 2 枚。

## 1. 検索条件は保存せず、選んだ作品だけを保存する

作者検索は作品を集める作業の道具で、コレクションの定義ではない。後から hm.db が
変わっても、メンバーが勝手に増えたり減ったりしないようにする。

> 旧実装 (`server/collection_generator.rb`) はルール (作家名への `artist LIKE` の
> 和集合) を正本にして毎回生成し直していた。そちらは採らない。

## 2. メンバーは `works.id` ではなく `source_url` で指す

`works.id` は hm.db の `images.id` で、hm.db を作り直すと変わる。コレクションは
人の手でしか作れず、画像キャッシュよりも作り直しが利かない。

副作用として、works に無い作品も指せる。引けないメンバーは管理画面に件数を出すだけで、
自動では消さない。館側で一時的に消えた作品が、次の export で戻ることがあるため。

## 3. `position` は連番にする。fractional indexing は採らない

2 件の間に挿すとき `(前 + 後) / 2` を入れて他の行に触らない方式は、double の仮数部が
53 bit しかないため、**同じ隙間へ 52 回挿すと中点が作れなくなる** (finder で実測)。
「この 2 枚の間にもう 1 枚」は手で並べていると起きやすい操作で、現実に壊れる。

並べ替えは、画面から全メンバーの並びを受け取って 0, 1, 2 … と振り直す。
1 コレクションはせいぜい数千件なので、全行の UPDATE で間に合う。

## 4. 公開範囲は `published` 列で持つ

作りかけのコレクションをトップに出さないため。一度公開したものを非公開に戻すと、
共有済みのリンクは 404 になる。

## 5. git へのエクスポートは引き継がない

finder は `collections.db` を YAML / CSV に書き出して git に置いていた。viewer_v2 は
VPS 上の管理画面で編集するので、手元の git に戻す経路が無い。アプリにバックアップ
機能は持たせず、VPS のスナップショットで守る。
